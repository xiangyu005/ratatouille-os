# 06-02｜正式設計文件規範

**文件狀態：成熟設計成果標準｜與 06 配套**

## 一、目的與適用原則

本文件定義遊戲設計逐漸成熟後的成果要求；初始整理依 [06-01](06-01_初始設計規劃指引.md)，共同政策依 [06](06_遊戲細部設計指引.md)。不以篇幅、表格數量或問題全部填滿判斷完成，也不要求組員一次寫完所有細節。

應讓未參與討論者理解玩家如何玩、世界如何運作、結果如何呈現，並掌握主要規則及跨系統關係。功能名稱、畫面清單或簡單流程不能代替設計。

## 二、實際遊玩流程

以代表性情境描述玩家如何進入活動、看到什麼資訊、如何操作、系統如何回應、結果如何形成，以及玩家能如何繼續下一步。交代操作前提與不同主要情況，不把自由活動寫成強制日程。

家庭、商店、餐廳等流程應能彼此銜接；手動、部分自動與全流程自動化若有差異，應說明執行者、玩家介入方式與結果。示例中的假設或數值須明示，不能自動變成正式規格。

## 三、機制、狀態、限制與恢復

說明必要條件、輸入的遊戲資訊、規則、關鍵狀態、狀態變化與結果。描述影響主要玩法成立的限制、資源不足、等待、中斷、交接、恢復及重要例外，不為補格式而增加不必要系統。

經營失敗須保留恢復路徑；數值與細則尚未確認時，標示未定及依賴，不自行填價格、門檻、公式或懲罰。人類已選定方案與待驗證內容保持區分。

## 四、玩家可觀察的資訊與回饋

交代玩家能看到的狀態、可用操作、限制原因、處理進度、結果與下一步依據。讓玩家理解操作與安排造成哪些改變，重要成長不能只留下抽象數值。

餐廳工作與自動化須能觀察顧客排隊、餐盤堆積、員工等待、資源使用與效率差異；效率定義未確認前，不將其當作可直接結算所有背景活動的倍率。

本標準要求介面功能與資訊需求；色彩、素材及正式美術規範由 `04` 承接並與 `13` 協調。

## 五、跨系統關係與規則歸屬

說明本領域需要其他系統的哪些規則或資料、會產生哪些影響、由哪份文件定義主要規則，以及尚未具備的前置條件。這裡描述遊戲層級資訊與意義，不要求資料表或 API。

改動跨越文件邊界時依 `06` 協調；主要規則只在其所屬文件維護，其他文件引用用途，避免各自重定義。版本或來源矛盾需列出並處理，不默默刪除。

## 六、決策理由、狀態與驗證

重要方案應留下理由、預期效果、來源與限制，採 `06` 的狀態分類。暫定規模與估算不能變成不可更動需求，AI 提出的內容須由人類確認。

說明已做過哪些模擬、試算、原型或遊玩測試及其結果，並引用 `14` 的紀錄；未測者列為待驗證，不宣稱通過。測試紀錄保留條件、原始結果、問題、調整理由及後續驗證，採用規則回寫所屬文件。

## 七、依領域性質調整完成標準

| 文件 | 成熟成果重點 |
|---|---|
| `07` | 足以統一角色、家庭、餐廳、小鎮、時代科技及比例的世界觀，供 `04` 建立美術依據；不強迫發展劇情任務或小說 |
| `08` | 時間、移動、互動、共同行為、場景外活動、暫停、跳時與保存恢復的共通規則 |
| `09` | 可理解的家庭生活與料理流程、營養與休息規則、知識庫建議到實際料理的銜接，以及資源不足恢復 |
| `10` | 可操作的採購、供應、交易與援助規則，以及與家庭庫存和餐廳補貨的邊界 |
| `11` | 完整客源、訂單、工作、設備、資源與自動化模型；行為和等待可觀察，玩家配置權明確 |
| `12` | 以既有玩法模型為依據的解鎖、投資、收支、成長與數值方案，保留假設及驗證結果 |
| `13` | 能銜接各玩法的操作、資訊回饋、引導與進階查閱，與 `04` 協調，不反向替未定玩法決策 |
| `14` | 持續累積的測試與調整紀錄，區分計畫與結果；不以單一模板或「最終版」要求所有測試一次完成 |

## 八、可交接至 16 的條件

所交接範圍應讓工程人員理解目標與適用範圍、玩家與其他角色行為、主要情境、規則與狀態、必要資訊、重要限制與恢復、跨系統責任，以及可觀察結果。重要未決問題、依賴與待驗證假設應明列，不能藏在默認值中。

成熟範圍可分階段交接，不要求所有文件按編號全數定案。`16` 再將企劃精煉為可實作、可驗收需求；`17～23` 承接模組、資料表、API、技術框架與演算法實作，**不要求遊戲企劃先寫 API、ERD 或程式模組**。

必要技術可行性研究可提前進行，但若限制改變玩法目標，應回到企劃協調。`14` 的遊玩驗證不取代 `24` 的功能、整合、效能與課程技術證據；課程要求依 `01`、候選映射依 `03` 承接，不宣稱尚未執行的技術已完成。
