# 06-01｜初始設計規劃指引

**文件狀態：初始規劃方法｜與 06 配套**

## 一、目的與使用方式

本文件說明負責人開始整理 `07～14` 時的工作方法。共同權限、全域方向、協調與 AI 協作依 [06](06_遊戲細部設計指引.md)；成熟成果依 [06-02](06-02_正式設計文件規範.md)。各領域的詳細任務已直接放入 `07～14`，本文件不重複整套清單。

初始文件應足以讓負責人知道已有什麼、還需設計什麼、哪些可以先做及需要誰提供條件，不要求預先填出所有答案。

## 二、先對照既有基礎

閱讀 `01～06` 與相關領域文件，辨識現行需求、流程、概念圖、核心目標及暫定規模。記錄文件名稱、章節或需求編號，不能只摘結論而遺失成立條件。

- 已有組員撰寫內容應整合保留，不以新模板清空。
- 遇到不同版本或互相矛盾的規則，保留雙方來源並標示待協調，不自行選邊覆蓋。
- 概念圖、流程示例、估算及候選清單不能直接升格為正式規則。
- 課程技術要求仍須承接，但候選映射不表示已採用、實作或驗證。

## 三、初始文件應整理的內容

| 項目 | 需要交代的內容 |
|---|---|
| 設計目標與範圍 | 領域要完成的體驗、責任及不負責的部分 |
| 既有需求與現行方向 | 有來源的功能、已確認原則及現行流程，保留限制與未定處 |
| 暫定規模與假設 | 用於討論或驗證的估算，不是固定物件清單或必達條件 |
| 需要新設計的機制 | 按設計項目整理工作，不先替負責人決定方案 |
| 既有流程需細化的項目 | 補足操作、規則、狀態、回饋及重要例外的工作 |
| 少數關鍵決策問題 | 真正影響玩法成立、邊界或選擇的問題 |
| 前置依賴與協調 | 所需規則／資料、來源文件、影響其他系統的結果及衝突 |
| 正式設計待補部分 | 指出成熟後應交付的玩法、規則及驗證內容，尚未定案就保留未定 |

不要求所有文件使用相同章節數量。`14` 以待驗證計畫、空白紀錄及後續實際結果為主，不套用一般玩法的最終版格式。

## 四、以設計項目為主，關鍵提問為輔

先整理需要完成的機制與流程，再提出少數關鍵問題。不要將每個細小例外改成問卷，也不要求每題都提交團隊決議。

具備前置條件者由人類負責人自行設計並記錄；未具備者註明依賴、所需成果及對應文件，不憑空寫死。其他不受阻部分可持續進行。互相依賴時先協調足夠支持雙方的共同規則。

方案若只影響本人文件，可依 `06` 自主決定；要求改變別人的規則、流程或資料定義時，再先協調。單純引用他人規則不需反覆確認。

## 五、標示狀態與決策依據

採用 `06` 的「既有／已確認方向」「暫定或待驗證」「待協調」「候選擴充」。沒有方案的設計工作直接標示待設計，不以已有標題或 AI 草稿冒充正式規則。

主要決策應留下理由及預期效果。AI 協助比較與整理，人類確認採用並審閱。若測試尚未執行，只能記錄驗證計畫，不能填入結果或通過狀態。

## 六、逐步演進為正式文件

各領域持續使用原檔，將人類已確認的規則寫入正文，保留未解問題及依賴，避免「初始版」與「正式版」雙軌衝突。遷移條文時保留需求來源、狀態及適用條件，其他文件改為引用主要規則。

當規則足以描述實際遊玩，再依 `06-02` 補齊成熟成果；設計中即可透過 `14` 累積模擬、試算或原型驗證，不必等待全部定案。
