## 1. 範圍與分層原則

- **演算法**是純函式：輸入資料、輸出結果，不讀寫 DB、不 import FastAPI／SQLite／NumPy／Numba。`core/tests/test_architecture.py` 會強制檢查。
- **世界裁決**在 `core/simulation`：讀世界狀態、呼叫演算法、把結果寫回狀態與事件。演算法不決定誰可以被指派，那是應用的責任。
- **Skill** 是給 FE 與 Agent 呼叫的可執行能力（`schedule_tasks` 等）；目前只有排程具備可對應的 trace 輸出，其餘 Skill 尚未建立。
- 同一策略若同時出現在料理工作與平台工作（例如 FCFS），只算一項演算法（`03` §6）。

## 2. 已實作：排程演算法

實作於 `core/algorithms/scheduling.py`，每項都是獨立函式，共用 `TaskSpec` 與 `ScheduleResult`。

| 名稱 | 函式 | 搶佔 | 可驅動世界指派 | 預設參數 |
|---|---|---|---|---|
| FCFS | `fcfs` | 否 | 是 | — |
| SJF | `sjf` | 否 | 是 | — |
| SRTF | `srtf` | 是 | 否 | — |
| Priority＋Aging | `priority_aging` | 否 | 是 | `aging_interval=5` |
| Round Robin | `round_robin` | 是 | 否 | `quantum=2` |

- 對外查詢用 `ALGORITHM_INFO`（`/api/v1/meta` 的 `algorithms`）；世界指派用 `ASSIGNABLE`（`/api/v1/meta` 的 `policies`）。
- **只有非搶佔式可以驅動 M1 的世界指派。** `SCHEDULE_QUEUE`／`SET_POLICY` 收到 `srtf`／`rr` 會回 422 `POLICY_NOT_ASSIGNABLE`，並在 `details.assignable` 列出可用清單。原因是 M1 的工作一旦開始就佔住 worker／station 到結束（見 §3），搶佔式排程會和世界模型矛盾；`11-04` 的預先權模型尚未實作，等它落地再放寬。
- 平手規則固定為 `(burst, arrival, id)` 或 `(remaining, arrival, id)`／`(-effective_priority, arrival, id)`，因此同一輸入永遠得到同一時間軸（`test_scheduling.py` 固定測資）。

### 2.1 輸入

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | str | 工作識別碼（世界內為 `T-0001`） |
| `arrival` | int | 到達時間（世界 `sim_time`，整數秒） |
| `burst` | int | 估計總工作量，必須 > 0 |
| `priority` | int | 數值越大越重要，預設 0 |

`arrival < 0` 或 `burst <= 0` 直接 `ValueError`；不得在演算法內靜默修正輸入。

### 2.2 輸出

| 欄位 | 說明 |
|---|---|
| `algorithm` | 顯示名稱（`FCFS`、`SJF`、`SRTF`、`Priority+Aging`、`RR`） |
| `order` | 第一次被選中的順序 |
| `completion_order` | 完成順序 |
| `start`／`finish` | 各工作第一次開始與最後結束時間 |
| `waiting`／`turnaround` | `finish - arrival - burst`（下限 0）／`finish - arrival` |
| `timeline` | Gantt 切片 `(task_id, start, end)`，搶佔式會有多段 |
| `trace` | 每一步的決策紀錄（§5） |
| `metrics` | 見 §2.3 |

### 2.3 指標定義

| 指標 | 定義 |
|---|---|
| `makespan` | 最後完成的時間 |
| `avg_waiting` | 平均等待時間（只計已完成工作） |
| `avg_turnaround` | 平均周轉時間 |
| `throughput` | 完成工作數 ÷ makespan |
| `cpu_utilization` | 總 burst ÷ makespan |

空輸入時 `makespan`、平均值與 `throughput` 皆為 0，不拋錯。這些是**平台指標**，不等於遊戲內「效率」；遊戲數值未定前不得把 `cpu_utilization` 當成收入或產能倍率（`03` §2、`14`）。

### 2.4 各策略行為

- **FCFS**：依 `(arrival, id)` 排序，後到者排在佇列尾；不因 burst 長短插隊。
- **SJF**：非搶佔；在「已到達且未完成」中選 burst 最短者。等待期間若無工作可跑，時間直接跳到下一個到達點（不倒填空轉）。
- **SRTF**：搶佔；每次在「已到達且未完成」中選剩餘時間最短者，只在有新工作到達或工作完成時切換，時間軸會出現同一工作的多段切片。
- **Priority＋Aging**：非搶佔；有效優先權 = `priority + (等待時間 ÷ aging_interval)`（整數除法），久候工作會逐步追上高優先權工作；`aging_interval<=0` 直接拒絕。
- **Round Robin**：固定時間片；時間片用完放回佇列尾，新到達者在同一時間點優先入列。

MLFQ 不在已實作清單（§7）。

### 2.5 已實作：快取與頁面置換演算法

實作於 `core/algorithms/caching.py`，共用 `CacheStep`、`TraceStep` 與 `CacheResult`，對應餐館備料快取區與食材換出需求（`03` G05、S05）。

| 名稱 | 函式 | 說明 | 測資標準 |
|---|---|---|---|
| FIFO | `fifo` | 最先進入者最先置換 | Silberschatz 20 步參照字串（15 misses, 5 hits） |
| LRU | `lru` | 最久未被使用（存取）者優先置換 | Silberschatz 20 步參照字串（12 misses, 8 hits） |
| LFU | `lfu` | 最不常使用（頻率最低）者置換，同頻採 FIFO 平手 | 參照串流頻率與平手置換測試 |
| Clock | `clock` | Second Chance 時鐘置換，維護參照位元與環狀指標 | 指標遍歷與參照位元清零／保留測試 |
| OPT | `opt` | Belady Optimal 離線最佳基準（最遠未來使用） | Silberschatz 20 步參照字串（9 misses, 11 hits） |

- 輸入：`references: list[str]`、`capacity: int`（容量必須 > 0）。
- 輸出：命中數 `hits`、缺失數 `misses`、命中率 `hit_rate`、各步狀態 `steps` 與 Skill `trace`。

### 2.6 已實作：記憶體與儲藏空間分區配置演算法

實作於 `core/algorithms/memory.py`，共用 `BlockSpec`、`MemoryRequest` 與 `MemoryResult`，對應餐館冷藏庫／儲藏貨架之空間分區配置（`03` G02）。支援固定分區（Fixed Partitions）與動態分割（Dynamic Partitioning）。

| 名稱 | 函式 | 策略邏輯 | 測資標準 |
|---|---|---|---|
| First-Fit | `first_fit` | 由前向後尋找第一個可容納空間 | Silberschatz Chapter 9 (100, 500, 200, 300, 600) |
| Best-Fit | `best_fit` | 尋找能容納且殘餘最小之分區（利用率最高） | 同上，在此測資下達成 100% 配置成功率 |
| Worst-Fit | `worst_fit` | 尋找最大之可用分區（保留最大殘餘空間） | 同上，評估殘留碎片效益 |

- 指標：`success_rate`（成功率）、`allocated_ratio`、`internal_fragmentation`（內部碎片）、`external_fragmentation`（外部碎片）。

### 2.7 已實作：死結防範與偵測演算法

實作於 `core/algorithms/deadlock.py`，共用 `SafetyResult`、`BankerRequestResult` 與 `DeadlockDetectionResult`，對應廚房多項設備併行申請之安全性與等待圖偵測（`03` G03）。

| 名稱 | 函式 | 核心功能 | 測資標準 |
|---|---|---|---|
| Banker's Safety | `bankers_safety` | 檢查系統是否具備安全序列（Safe Sequence） | Silberschatz Chapter 8 經典五行程三資源 |
| Banker's Request | `bankers_request` | 模擬申請分配並驗證狀態安全性（防範死結） | 循序測試 P1 申請 (1,0,2) 獲准、P0 (0,2,0) 不安全拒絕 |
| WFG Cycle Detection | `detect_deadlock_wfg` | 單一實例等待圖（Wait-For Graph）環路偵測 | 有向圖環路與死結行程識別 |
| Matrix Detection | `detect_deadlock_matrix` | 多實例資源死結偵測矩陣演算法（資源回收推進） | 多實例互鎖死結識別與安全推進清單 |

## 3. 世界資源模型

M1 的世界資源是**人**與**工作站**兩種可數資源，外加單調前進的模擬時間。

| 實體 | 狀態 | 資源語意 |
|---|---|---|
| `Worker` | `idle`／`busy` | 一次只能執行一件工作；`task_id` 指出目前工作 |
| `Station` | `free`／`busy` | 同上；未指定 `station_id` 時由系統挑 `id` 最小的空閒站 |
| `Task` | `queued`／`running`／`done` | `remaining_seconds`、`started_at`、`finished_at` 記錄進度 |

- **非搶佔**：`ASSIGN_TASK` 與 `SCHEDULE_QUEUE` 只會把 `idle` worker 與 `free` station 配給 `queued` 工作；已開始的工作只能靠 `ADVANCE_TIME` 完成。
- **時間推進**：`ADVANCE_TIME {seconds}` 依到期時刻逐段推進，把到期工作標成 `done` 並釋放 worker／station；**同刻到期的工作依 `task_id` 排序**，因此事件順序可重現。跳時不會重算已完成結果，也不改變工作的耗時定義（`17` §5.4）。
- **事件與狀態一致**：每個 command 在單一交易內寫入 event、snapshot、idempotency；交易成功後才廣播 WebSocket。
- **資源等待**：目前沒有等待佇列或公平性保證——沒有空閒 worker／station 時，`SCHEDULE_QUEUE` 只會少配幾件工作，並在 `QUEUE_SCHEDULED` 回報 `assigned` 數量，不會排隊補位。

## 4. 效能與 Numba 政策

`17` §11.4 的規則：

1. 先量測再優化，profiler 證據要留在紀錄裡。
2. CORE tick 預算固定（每 tick < 5 ms，依硬體調整），超過必須記錄。
3. 大批量模擬才考慮 Numba；**API／DB／JSON 不進 Numba**。
4. FE 不每幀重繪整個 world，只以事件更新局部元件。

現況（2026-11-02，單機、單 worker）：

| 項目 | 數值 |
|---|---|
| `POST /api/v1/commands` p50 | 2.23 ms |
| `POST /api/v1/commands` max | 3.65 ms |
| 30 個工作的單次排程 | FCFS 0.07、SJF 0.17、Priority+Aging 0.23、RR 0.22、SRTF 0.27 ms |

- 過去 p50 約 11.5 ms、尾端 16.4 ms，主因是每個 command 開兩條新 SQLite 連線重跑 WAL PRAGMA；改成釘住的單一連線後才符合預算。量測方法與前後對照見 [24](24_系統測試與品質驗證紀錄.md)。
- **目前沒有任何 Numba kernel。** `ai/.venv` 有 0.68.1 並通過 `njit(cache=True)` smoke，但 CORE 的演算法仍是 reference 實作。未來加 kernel 的條件：profiler 指出演算法本身是 hotspot，且能證明與 reference 在同一固定 workload 得到相同結果。
- 已知下一個瓶頸不是演算法，而是每個 command 都寫整份世界 snapshot（7.2 KB，隨狀態線性成長）。

## 5. Skill 對照

排程決策會留下 `trace`，每一筆長這樣：

```json
{"step": 2, "skill": "schedule_tasks", "algorithm": "SJF",
 "package": "core.algorithms.scheduling",
 "input": {"time": 3, "ready": ["T-0002", "T-0003"]},
 "output": {"selected": "T-0003"}}
```

| Skill（規劃） | 目前狀態 | 對應實作 |
|---|---|---|
| `schedule_tasks` | 部分：演算法與 trace 已有，尚未包成 MCP tool | `core/algorithms/scheduling.py` |
| 空間配置（First／Best／Worst Fit） | 部分：演算法與 trace 已實作，可評估利用率與碎片 | `core/algorithms/memory.py` |
| 設備管理（Banker's／Deadlock） | 部分：安全序列檢查、資源申請模擬與死結偵測已實作 | `core/algorithms/deadlock.py` |
| 快取管理（FIFO／LRU／LFU／Clock／OPT） | 部分：演算法與 trace 已實作，具備固定參照串流驗證 | `core/algorithms/caching.py` |
| 知識庫（檢索、引用） | 未實作（AI 服務本體未建立） | `ai/` 僅依賴與 DB |
| AI 工作分派（local／cloud） | 未實作 | 無 |

Skill 的拆分依職責，不要求一演算法一 Skill 一頁面（`03` §5）。

## 6. 驗證方式

| 項目 | 方式 |
|---|---|
| 排程演算法正確性 | 固定 workload 的手算預期值（`core/tests/test_scheduling.py`） |

| 決定性 | 同 seed／同 command → 同事件序列（`core/tests/test_world.py`） |

## 8. 待決問題

1. `11-04` 的預先權／實際執行權模型落地後，`ASSIGNABLE` 是否納入搶佔式策略，以及切換成本如何計入 `sim_time`。

4. 工作可中斷性由誰決定：資料欄位、工作類型，還是設備屬性。
5. 資源不足時的行為（排隊、失敗、降級）尚未定義，目前只少配工作。
6. 12 項課程演算法的正式清單與計數口徑（`03` §6）。
