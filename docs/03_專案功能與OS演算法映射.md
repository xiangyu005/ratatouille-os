## 1. 映射原則

**核心功能 → 需要解決的問題 → 候選演算法或策略組 → 執行及比較結果 → Skill 封裝與驗證。**

同一功能可支援多種解決相同問題的策略，共用輸入資料與結果比較方式。OS 管理為官方推薦的玩家選用方向，需等基礎玩法與管理問題成熟後再規劃具體操作。以下演算法均為候選，尚未正式採用；課程要求仍須由系統滿足。

### 使用層級

| 層級           | 作用                     | 例子與限制                                            |
| -------------- | ------------------------ | ----------------------------------------------------- |
| 玩家可選策略   | 讓玩家依情境調整管理方式 | 官方推薦、玩家自己用（GAME-21）；具體策略與操作待規劃 |
| 系統正確性機制 | 維持共享資源及狀態正確   | Mutex、Semaphore；須有實際競爭及保護對象              |
| 平台內部機制   | 支援知識庫與 AI 系統     | 工作排程、快取、匯入、權限等                          |

### 適配標記

- **高適配**：功能具有明確的演算法應用情境。
- **條件適配**：需補充規則或模型。
- **暫不映射**：目前不需要指定 OS 演算法，保留一般業務邏輯即可。

## 2. 遊戲核心功能與候選策略組

### G01｜餐點製作與工作排程

需求來源：GAME-05、GAME-13、GAME-18、GAME-21。

已知工作為取食材、放置烹飪台、灶台互動做菜、上菜及收洗餐盤。家庭員工依工作表執行，主角用管理面板安排；僅主角可直接操控。以整筆餐點或各步驟作為排程單位、耗時、優先權及可中斷性仍待規劃。

決策問題：多個料理工作等待執行時，如何決定處理順序及執行時間分配？

| 候選            | 應用方式                             | 適配與前提                                 |
| --------------- | ------------------------------------ | ------------------------------------------ |
| FCFS            | 依工作進入順序處理                   | 高；需有到達順序及可執行工作佇列           |
| SJF             | 優先處理預估時間較短的工作           | 高；需可比較的預估處理時間                 |
| SRTF            | 優先執行剩餘時間最短的工作           | 條件；工作須可中斷與恢復                   |
| Priority＋Aging | 依優先權處理，逐漸提高久候工作優先權 | 高；需明確優先權及老化規則                 |
| Round Robin     | 以時間片輪流執行工作                 | 條件；工作可切分，且時間片及切換成本有定義 |
| MLFQ            | 依工作行為調整所在佇列               | 條件；需佇列層級、升降規則及適用工作類型   |

共用資料：工作 ID、到達時間、預估處理時間、優先權、剩餘工作量及狀態。比較結果可包含完成順序、等待時間、周轉時間及切換次數；正式指標與定義待細部規劃。

不同策略應使用相同工作集及資源條件。料理能否中斷、如何將訂單拆成工作，以及設備等待與處理時間如何區分，尚待確認。不能把不可中斷的料理直接視為適用 SRTF 或 RR。

### G02｜餐廳儲藏空間配置

需求來源：GAME-12、GAME-14、GAME-19。

餐廳以小冰箱作為初始儲存設備，設定補貨後每日 8:00 自動送入餐廳並扣款。容量、入庫限制與空間區塊模型未定，尚不能直接認定 Fit 策略已適用。

決策問題：有限儲藏空間如何分配給不同食材的空間需求？

| 候選      | 應用方式                       | 適配與前提                       |
| --------- | ------------------------------ | -------------------------------- |
| First Fit | 選第一個能容納需求的可用區塊   | 高適配候選；須先建立空間區塊模型 |
| Best Fit  | 選能容納且配置後剩餘最小的區塊 | 高適配候選；同上                 |
| Worst Fit | 選剩餘空間最大的可用區塊       | 高適配候選；同上                 |

共用資料：區塊順序與容量、可用空間、食材需求量。可比較配置成功率、剩餘容量及碎片。

待確認：儲存區塊、空間分割與釋放方式、食材可否拆分，以及不同保存條件的限制。

升級可能改變容量或空間結構，讓原策略需重新評估；不在此指定固定升級路線。家庭與餐廳仍使用獨立庫存。

### G03｜餐廳設備與工作資源管理

需求來源：GAME-05、GAME-13、GAME-18。

已知工作位置包含烹飪台、灶台及流理臺，可用人力受營養狀態影響。設備占用、釋放及同時工作規則尚未確定；不能僅憑場景設備就認定同步機制已完成。

管理問題：多項工作使用有限設備，如何保護資源並處理等待及安全分配？

| 候選演算法／機制   | 實際用途                         | 適配與前提                                       |
| ------------------ | -------------------------------- | ------------------------------------------------ |
| Mutex              | 保護只能單獨使用的資源或共享狀態 | 高；須有互斥對象及競爭存取                       |
| Semaphore          | 限制同時使用某類設備的工作數     | 高；需定義設備數與取得／釋放流程                 |
| Banker's Algorithm | 申請多類資源時檢查分配後的安全性 | 條件；需 Available、Allocation、Max／Need 等模型 |
| Deadlock Detection | 偵測等待關係是否形成死結         | 條件；需相符的資源及等待模型，並規劃偵測後處理   |

共用資料：工作資源需求、設備數量、配置／占用狀態及等待關係。可觀察資源使用、等待、安全序列或偵測結果。

這些機制不全是替代方案。互斥與計數同步保護操作；銀行家檢查安全分配；死結偵測檢查既有狀態。不能放在同一個「選最快策略」選單中，也不能以畫面上排隊代替同步實作。

### G04｜地圖移動與多目的地安排

需求來源：GAME-08～11。

玩家可自由選擇目的地，家庭由主角到商店採購，路程可跳過相應時間；餐廳使用設定後自動配送，不預設需要玩家規劃配送路線。

多目的地排序仍未確定，下列全部為條件候選。

| 候選   | 可能模擬方式                 | 需滿足的模型               |
| ------ | ---------------------------- | -------------------------- |
| FCFS   | 依目的地加入順序處理         | 多個待處理目的地           |
| SSTF   | 先處理離目前位置最近的目標   | 可比較的位置距離           |
| SCAN   | 沿方向處理，到邊界再反向     | 一維有序位置、方向與邊界   |
| C-SCAN | 單向處理，到邊界後回起點     | 一維位置及回程成本定義     |
| LOOK   | 到該方向最遠待處理位置再反向 | 一維位置、待處理集合與方向 |

SSTF、SCAN、C-SCAN、LOOK 原為磁碟排程方法，不是一般道路導航演算法。用於地圖時需清楚標示為模型應用或教學模擬，不把任意二維導航說成真正磁碟排程。

### G05｜食材、營養及知識查詢

需求來源：GAME-06、07、16、17、SYS-01、03。

營養師提供料理營養屬性並自動規劃飲食策略，家庭員工營養不足時無法工作。營養值、門檻與飲食策略的評估方式未定，不在此預設最佳化方法。

食譜與食材資訊用於理解料理需求及營養選擇，目前不強配特定 OS 演算法。查詢所需的檢索、快取與 AI 工具可由平台能力支援，不需另外新增營養玩法來湊演算法。

庫存分離本身是資料及業務規則；依期限選用食材屬一般庫存策略。兩者均不直接當作已實作的課程 OS 演算法。

### G06｜升級與自動化

需求來源：GAME-14、15、20。

升級可能改變資源數量、容量、管理限制及自動化能力，主要作用是改變其他策略面對的問題條件。升級本身不指定固定 OS 演算法，也不預設每個系統可升級。

後期老鼠機器人為正式需求方向，能工作更久且不需食物營養；加入方式與能力依遊戲規模規劃。機器人不直接算作新增演算法。

自動化的具體工作確定後，再分析需用的排程、配置或同步；原草案 LV2／LV3 不作為演算法情境已成立的依據。

## 3. 課程平台功能與候選演算法

此處為系統需求，不要求全部轉為玩家可見策略。

| 編號 | 平台功能及來源                        | 候選                          | 用途、前提及觀察結果                                                       |
| ---- | ------------------------------------- | ----------------------------- | -------------------------------------------------------------------------- |
| S01  | AI 任務與資料工作排程；SYS-04、08、09 | FCFS、SJF、SRTF、RR、Priority | 管理工作佇列；各策略仍受可中斷性等前提限制；記錄等待、完成及處理順序       |
| S02  | 多工作同步；SYS-02、05、11            | Mutex、Semaphore              | 保護共享資料及限制並行數；需競爭存取與正確的取得／釋放                     |
| S03  | 資料匯入；SYS-02                      | Producer–Consumer             | 不同處理階段速度不一時，控制有界緩衝與生產／消費；觀察占用與阻塞           |
| S04  | 系統資源管理；SYS-08、11              | Banker's、Deadlock Detection  | 檢查安全分配或等待；需有相符資源模型，不以一般資源檢查代替                 |
| S05  | 快取管理；SYS-03、09                  | FIFO、LRU、OPT                | 相同請求序列及容量比較命中／缺失；OPT 需已知未來序列，適合作離線基準       |
| S06  | 檔案讀取排程；SYS-09                  | FCFS、SSTF、SCAN、LOOK        | 須定義讀取請求及位置模型；一般檔案查詢不代表應用程式實際控制磁碟排程       |
| S07  | 資料存取權限；SYS-09、11              | ACL                           | 依角色或主體控制資源讀寫，呈現允許／拒絕；是否納入十二項須核對課程計數口徑 |

### 地端／雲端 AI 工作分派

SYS-07、08 要求同時具備兩種環境，並依 CPU、GPU、記憶體、I/O、任務優先權及排程規則選擇執行位置，保留理由與結果。

工作「先做哪個」與「在哪裡執行」是相關但不同的決策。可由排程、資源檢查及安全分配共同支援，但有地端／雲端切換，不等於已完成一項 CPU 排程演算法；銀行家亦不能單獨代替完整的 AI 工作分派設計。

## 4. 優先研究順序

| 優先研究組            | 候選                                                  | 優先理由                         | 正式採用前缺口                               |
| --------------------- | ----------------------------------------------------- | -------------------------------- | -------------------------------------------- |
| A. 料理／系統工作排程 | FCFS、SJF、SRTF、RR、Priority＋Aging；MLFQ 為延伸候選 | 共用工作模型，可比較多種處理方式 | 工作來源、可中斷性、資源等待、時間及指標模型 |
| B. 餐廳空間配置       | First Fit、Best Fit、Worst Fit                        | 既有儲存需求，可與升級連動       | 區塊、分割／釋放、食材需求及保存限制         |
| C. 設備資源管理       | Mutex、Semaphore、Banker's、Deadlock Detection        | 既有料理可能形成設備競爭         | 競爭、配置、最大需求及等待／恢復模型         |
| D. 平台快取           | FIFO、LRU、OPT                                        | 指定平台能力，便於同序列比較     | 容量、請求序列、快取單位與離線基準定位       |

料理工作排程及儲藏空間配置為優先規劃方向，需先確定輸入、輸出、用途與驗證方式。

## 5. Skill 規劃方向

| 功能組      | 候選職責                                 |
| ----------- | ---------------------------------------- |
| 工作排程    | 讀取工作、執行排程、計算指標、比較策略   |
| 空間配置    | 讀取容量、執行配置、輸出配置及剩餘空間   |
| 設備管理    | 檢查、申請、釋放資源、更新占用及偵測等待 |
| 快取管理    | 管理快取、執行置換、統計命中與缺失       |
| 知識庫      | 匯入、清理、索引、檢索、來源引用及問答   |
| AI 工作分派 | 取得資源狀態、評估執行環境、分派及記錄   |

本表是責任分析，不是正式的 25 個 Skill 清單。後續依可獨立執行的職責拆分，明確輸入輸出，提供 SKILL.md 及程式；避免只為數量拆出沒有獨立用途的工具。

UI 與 Agent 應取得同一可執行能力的實際結果；Agent 透過 MCP 使用工具。演算法是否各自一個 Skill，應依職責決定，不要求一演算法、一 Skill、一網頁互相一對一。

## 6. 演算法驗證與計數原則

正式採用每個候選前，需補齊以下紀錄：

| 項目       | 應記錄內容                                 |
| ---------- | ------------------------------------------ |
| 需求來源   | SYS／GAME，若依賴 PROP 則標示其採用狀態    |
| 問題與用途 | 實際決策、共享資源或系統限制               |
| 前提與輸入 | 工作、資源、容量、位置或請求模型及參數     |
| 執行結果   | 決策、狀態變化、步驟紀錄及統計             |
| Skill 對應 | 負責運算或呼叫的工具及輸入輸出             |
| 驗證方法   | 固定測資、預期結果、課堂工具或程式比對     |
| 應用性質   | 遊戲策略、實際系統機制或教學模擬           |
| 採用狀態   | 候選、模型已確認、已實作、已驗證，分開記錄 |

跨功能共用的同一演算法不得重複計數；不能因 FCFS 同時用於料理和平台，就算成兩項。Priority＋Aging 等組合、Mutex／Semaphore／ACL 等機制的計數口徑，需核對老師規範，不能僅依名稱拆項。

候選演算法概況如下，跨功能重複使用的演算法不重複計數：

| 類別           | 候選數 | 限制                                                         |
| -------------- | ------ | ------------------------------------------------------------ |
| 排程           | 6      | FCFS、SJF、SRTF、Priority＋Aging、RR、MLFQ；部分需可中斷模型 |
| 空間配置       | 3      | 需建立可配置區塊模型                                         |
| 同步與死結     | 4      | 不同職責；須符合各自前提與計數口徑                           |
| 快取置換       | 3      | OPT 為離線比較基準                                           |
| 磁碟／路線排程 | 5      | 含重複的 FCFS；位置模型及模擬定位待確認                      |
| 存取權限       | 1      | ACL 是否計入需核對                                           |

Producer–Consumer 另列於平台映射。正式採用數量待確認使用模型與驗證方式後統計。

## 7. 待決策事項

1. 顧客點餐如何形成工作資料、工作粒度及可中斷／恢復能力。
2. 儲藏庫是否採用符合 Fit 策略的區塊配置模型。
3. 人員、設備與資料是否有真實或明確模擬的競爭、等待及資源釋放。
4. 已確認推薦選用的 GAME-21 如何操作、比較結果，以及哪些機制由系統自動處理。
5. 哪些平台機制屬正式課程演算法，以及跨情境計數與組合策略的認定。
6. 地圖是否真的需要多目的地排序；未確認前不強配磁碟排程。
7. 最終演算法清單、Skill 職責、測資、驗證工具及負責人。
